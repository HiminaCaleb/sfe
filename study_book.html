1.1 Software Engineering Concepts

Software engineering is the application of a systematic, disciplined, and quantifiable approach to the development, operation, and maintenance of software. The goal is to produce reliable, efficient, and maintainable software on time and within budget.

Systems Development Life Cycle (SDLC)

The SDLC is the overarching framework that describes the phases of developing an information system. Two dominant approaches exist:

Predictive / WaterfallSequential phase-by-phase development. All requirements gathered upfront before any coding begins.Fixed scope; formal documentation; phase gates; plan-drivenRequirements are stable, well-understood, and unlikely to change
Agile / IterativeIncremental delivery in short cycles (sprints/iterations). Requirements emerge and evolve.Flexible scope; working software over documentation; customer collaboration; continuous deliveryRequirements are uncertain, changing, or complex; need fast delivery of working features

1.2 Attributes of Good Software

Good software satisfies its requirements AND possesses non-functional qualities that make it maintainable and fit for its environment.

AttributeDefinitionHow It Is Measured / Achieved
CorrectnessSoftware does exactly what the specification requires — no more, no less.Testing against requirements; formal verification
ReliabilitySoftware performs its intended function without failure under stated conditions for a stated period of time.Mean Time Between Failures (MTBF); fault tolerance mechanisms
EfficiencySoftware makes optimal use of system resources (CPU, memory, bandwidth).Performance profiling; benchmarking; Big-O analysis
MaintainabilitySoftware can be easily modified to correct defects, improve performance, or adapt to a changed environment.Low coupling; high cohesion; clean code; documentation
PortabilitySoftware can be transferred from one hardware/software environment to another with minimal effort.Platform-independent coding; abstraction layers
UsabilitySoftware is easy to understand, learn, and operate by intended users.Usability testing; user satisfaction surveys; SUS scores
SecuritySoftware protects against unauthorized access, data breaches, and malicious attacks.Penetration testing; code reviews; threat modelling

ReusabilityComponents can be reused across different parts of the system or in future projects.OOP principles; design patterns; component libraries
Good software ALWAYS satisfies BOTH functional requirements (what it must do) AND non-functional requirements (how well it does it). Know at least 5 attributes and be able to explain each in the context of a scenario.

1.8 Event Decomposition Technique

Event decomposition is a technique used to identify use cases by asking: "What events occur in the environment to which the system must respond?"

Types of Events

Event TypeDefinitionTriggerExample
External EventAn event that occurs outside the system, triggered by an external actor (usually human)Actor initiates an actionCustomer places an order; employee submits a leave request
Temporal EventAn event triggered by the passage of time — the system must act at a specific timeA point in time or elapsed timeGenerate monthly payroll report on the 25th; send reminders 3 days before deadline
State Event (Internal)An event that occurs when something inside the system reaches a certain state or conditionAn internal condition is metInventory drops below reorder level; account balance falls below minimum

Event Decomposition Process

  1. Identify all events in the problem domain
  2. For each event, define one use case that the system must support to handle that event
  3. Each use case handles exactly ONE event (one-to-one mapping)
  4. Group related use cases into subsystems using package diagrams
Key Rule
Each event → one use case. Each use case name starts with a verb (e.g., "Process Customer Order", "Generate Monthly Report", "Update Inventory Level").

2.2 The Fraud Triangle

The Fraud Triangle, developed by criminologist Donald Cressey, explains why ordinary people commit fraud. All three elements must be present simultaneously for fraud to occur.

The Fraud Triangle
💰
INCENTIVE / PRESSURE
Financial need, greed, gambling debts, lifestyle pressure, management pressure to meet targets
🔓
OPPORTUNITY
Weak controls, access to assets, lack of supervision, no separation of duties, override ability
🧠
RATIONALISATION
"I'll pay it back", "I deserve it", "Everyone does it", "The company owes me", "It won't hurt anyone"
ElementDefinitionExamplesControls to Address It
Incentive / PressureThe motivation that drives the individual to commit fraud — financial or psychological pressureCrushing personal debt; unrealistic sales targets; addiction; greedFair compensation; employee assistance programs; realistic targets; mental health support
OpportunityThe circumstances that allow fraud to occur — usually weak or absent controlsSingle person controlling accounts payable AND payment; no audit trails; override accessSeparation of duties; mandatory leave; job rotation; strong internal controls; audit trails
RationalisationThe fraudster's self-justifying belief that what they are doing is acceptable or not truly wrong"The company overcharges customers so this is just equalising it"; "I'll repay it next month"Ethics training; strong ethical culture; whistleblower programmes; background checks
Exam Critical Point
The fraud triangle states that fraud ONLY occurs when ALL THREE elements are present. Removing ANY one element prevents fraud. Controls should target OPPORTUNITY (the most controllable element).

2.3 Encryption Methods

Encryption transforms readable plaintext into unreadable ciphertext using an algorithm (cipher) and a key. Only authorised parties with the correct key can decrypt and read the data.

Sender and receiver must both have the shared key.Fast; efficient for bulk data; key sharing is the security problemEncrypting data at rest (disk encryption); encrypting database content; bulk data transfer after handshakeAES (Advanced Encryption Standard), DES, 3DES, RC4, Blowfish
Asymmetric EncryptionPublic-key encryptionUses a KEY PAIR: a PUBLIC key (freely shareable) to encrypt and a PRIVATE key (secret) to decrypt. Key Encryption Concepts

ConceptDefinition
Digital SignatureUses asymmetric encryption to prove authenticity and non-repudiation. Sender encrypts a hash of the message with their PRIVATE key. Receiver decrypts with the sender's PUBLIC key to verify identity and integrity.
Digital Certificate (PKI)A document issued by a Certificate Authority (CA) that binds a public key to an identity (person, server). Enables trust in public keys.
SSL/TLSProtocols that establish an encrypted connection between client and server. TLS is the modern, more secure successor to SSL. Used in HTTPS.

3.1 Use Case Diagram

A Use Case Diagram is a behavioural UML diagram that represents the functional requirements of a system from the perspective of external users (actors). It shows WHAT the system does, not HOW it does it.

Theory

  • Developed during the Requirements/Analysis phase
  • Shows the boundary of the system (what is inside vs. outside)
  • Identifies all actors and the use cases they participate in
  • One use case per event (from event decomposition)
  • Does NOT show the sequence, flow, or internal logic of the system

Notation Rules Table

ElementNotationRules & Description
System Boundary[ Rectangle ]A rectangle enclosing all use cases. The system name is written at the top inside or above the rectangle. Actors are OUTSIDE the boundary.
Actor (Primary)Stick figureDrawn OUTSIDE the system boundary. Actor name written below the stick figure. Initiates the use case. Typically on the LEFT side of the diagram.
Actor (Secondary)Stick figureDrawn OUTSIDE the system boundary. Participates in but does not initiate the use case. Typically on the RIGHT side. Can also be another system.
Use Case( Oval )Drawn INSIDE the system boundary. Name is a verb phrase (e.g., "Process Order"). Each oval = one use case = one event.

3.2 System Sequence Diagram (SSD)

A System Sequence Diagram is a UML interaction diagram that shows the sequence of input/output messages (system events) between external actors and the system as a whole (treated as a black box) for ONE specific use case scenario.

Theory

  • Shows the WHAT of interactions — inputs actors send to the system and outputs the system returns
  • The system is treated as a SINGLE BLACK BOX (one lifeline labelled ":System")
  • Developed during the Analysis phase — before internal design is done
  • One SSD per use case scenario (happy path typically, and sometimes one per alternative)
  • Shows the boundary of the system clearly
  • Messages become method calls in the design sequence diagram

3.3 State Machine Diagram

A State Machine Diagram (also called a Statechart Diagram) shows how a single object or system changes state in response to events throughout its lifecycle. It models the dynamic behaviour of one entity.

Theory

  • Models the lifecycle of a SINGLE object (e.g., an Order, a Customer Account)
  • Useful for objects that have distinct, identifiable states with different behaviour
  • Every object starts in some state and ends in some state
  • A state represents a period during which an object is waiting for an event or performing an activity
  • A transition is a change from one state to another triggered by an event
  • Syntax of a transition label: event [guard] / action

3.4 Initial Design Class Diagram (IDCD)

A Design Class Diagram shows the static structural design of the system — the classes, their attributes, methods, and the relationships between them. The Initial Design Class Diagram is developed early in design, before full method signatures are defined.

Theory

  • Developed during the Design phase
  • Each class has three compartments: Name, Attributes, Methods/Operations
  • Class names are nouns, written in PascalCase
  • Attributes follow format: visibility name: type [= default]
  • Methods follow format: visibility name(params): returnType
  • Relationships define how classes interact
  • The IDCD is derived from: domain model, use cases, and design decisions

3.5 Package Diagram

A Package Diagram is a structural UML diagram that groups related classes (or use cases) into packages (subsystems), showing the high-level organisation and dependencies between packages.

Theory

  • Used to organise large, complex systems into manageable subsystems
  • Packages can represent layers (Presentation, Business Logic, Data Access), modules, or functional areas
  • Shows DEPENDENCIES between packages — if Package A uses something from Package B, A depends on B
  • A dependency means: changing Package B could require changes in Package A
  • Goal: minimise dependencies and ensure they go in one direction (avoid circular dependencies)

3.6 PERT Chart

A PERT (Program Evaluation and Review Technique) Chart is a project management tool that illustrates project tasks, their dependencies (what must be done before what), and the critical path — the longest sequence of tasks that determines the minimum project duration.

Theory

  • Developed by the U.S. Navy in the 1950s for the Polaris missile project
  • Used for scheduling, coordination, and control of complex projects
  • Shows activities as nodes (Activity-on-Node / AON) or as arrows (Activity-on-Arrow / AOA)
  • Identifies the Critical Path — the longest path through the network
  • Tasks on the critical path have ZERO slack/float — any delay delays the entire project
  • Tasks NOT on the critical path have positive slack — they can be delayed without affecting the project end date

How to Calculate Critical Path — Step-by-Step

  1. Forward Pass: Start from the first node. ES of first activity = 0. Calculate EF = ES + Duration for each activity. ES of each activity = max EF of all its predecessors.
  2. Backward Pass: Start from the last node. LF of last activity = its EF (project end date). Calculate LS = LF − Duration. LF of each activity = min LS of all its successors.
  3. Calculate Slack: Slack = LS − ES (or LF − EF) for each activity.
  4. Identify Critical Path: Activities with Slack = 0 form the critical path.

4.3 Coupling and Cohesion

Coupling — How Dependent Classes Are on Each Other

Coupling measures how strongly connected two classes or modules are. The goal is LOW (loose) coupling.

Coupling LevelDescriptionDesirability
Content Coupling (worst)One module directly modifies the internal data of another❌ Worst — avoid
Common CouplingMultiple modules share global data❌ Very bad
Control CouplingOne module passes control flags to another, affecting its behaviour⚠️ Bad
Stamp CouplingModules share a complex data structure but only use parts of it⚠️ Acceptable sometimes
Data CouplingModules share only simple data through parameters — no control flags✅ Good
Message Coupling (best)Modules communicate only through well-defined interfaces/messages with no shared data✅ Best
Low Coupling Benefits
Changes in one class don't ripple through to many other classes. Classes are more reusable and independently testable. System is easier to maintain.

Cohesion — How Related the Responsibilities of a Single Class Are

Cohesion measures how strongly the elements within a single module belong together. The goal is HIGH cohesion.

Cohesion LevelDescriptionDesirability
Functional (best)All elements contribute to a single, well-defined function✅ Best
SequentialOutput of one element is input to the next✅ Good
CommunicationalElements operate on the same data structure✅ Good
ProceduralElements follow a specific sequence of steps⚠️ Moderate
TemporalElements are grouped because they execute at the same time⚠️ Moderate
LogicalElements perform similar operations (e.g., all I/O operations)❌ Weak
Coincidental (worst)Elements grouped arbitrarily — no logical relationship❌ Worst — avoid

Q1.3 — Purpose of Systems Analysis (5 marks) SFE316D Paper A 2023 · Q1.3

Explain the purpose of systems analysis and outline the benefits of analysing a system before implementation. (5)
🧠 THINKING GUIDE:
  1. Define systems analysis (1 sentence = ~1 mark).
  2. Then list/explain at least 4 benefits of analysis BEFORE implementation (1 mark each).
  3. Benefits should be practical: cost, risk, user satisfaction, correct requirements.
📚 CONCEPT APPLIED: SDLC Analysis Phase; Systems Analysis Activities (Satzinger Ch.2).
✅ FULL ANSWER:

Purpose of Systems Analysis: Systems analysis is the process of understanding and documenting the requirements and processes of a business system so that the new system can be designed to meet those needs accurately. It involves gathering detailed information, defining requirements, modelling processes, and prioritising requirements in collaboration with stakeholders.

Benefits of Analysing Before Implementation:

  1. Reduces Cost of Errors: Defects discovered in analysis cost far less to fix than defects found after implementation. The cost of fixing a requirements error post-deployment can be 100× higher than fixing it upfront.
  2. Ensures Correct System is Built: Analysis ensures the development team understands what users actually need — not just what they said they wanted. This prevents building the wrong system.
  3. Identifies Scope: Analysis defines the scope — what is IN the system and what is OUT. This prevents scope creep and ensures budget/schedule can be planned accurately.
  4. Reveals Hidden Requirements: Through interviews, observation, and document analysis, implicit requirements are uncovered that users never explicitly stated but expect the system to support.
  5. Stakeholder Alignment: Analysis brings all stakeholders together early, resolving conflicts between different user groups' requirements before expensive design and coding begin.

Q3.1 — Two Techniques to Identify Use Cases (4 marks) SFE311T Formative Test 1 2023 · Q3.1
QUESTION AS-IS:
Describe two (2) techniques for identifying use cases. Which is the most comprehensive approach? (4)
🧠 THINKING GUIDE:
  1. The two techniques are: (1) User Goal Technique and (2) Event Decomposition Technique.
  2. Each technique = 1 mark for name + 1 mark for description = 2 marks each = 4 marks total.
  3. Most comprehensive = Event Decomposition (it finds ALL events including temporal and state events, not just user-initiated goals).
✅ FULL ANSWER:
  1. User Goal Technique (2 marks): Identify users (actors) and ask them what goals they want to accomplish with the system. Each goal becomes a use case. The analyst interviews different types of users and probes to refine these goals into specific use cases. Example: Ask a "Car Owner" what they want to accomplish → "Book a car wash", "Cancel booking", etc. Limitation: Only finds user-initiated interactions — misses temporal and state events.
  2. Event Decomposition Technique (2 marks): Identify all events in the environment to which the system must respond. For each event, define one use case that represents the system's response. Events can be: external (triggered by actors), temporal (time-based), or state events (internal condition reached). This is the most comprehensive approach because it identifies ALL types of events, not just user-initiated ones, resulting in a more complete use case model.
Most Comprehensive
Event Decomposition Technique — because it captures external, temporal, AND state events. The user goal technique misses temporal events (e.g., "Generate monthly report on the 25th") and state events (e.g., "Stock falls below reorder level").
